# 02 · 心智架构：四要素、环路、主动性阶梯与端到端卡点

## 2.1 心智的第一性拆解：四个可独立验证的工程要素

| 要素 | 定义 | 现状（设计时点） |
|---|---|---|
| 记忆（面向过去） | 知道发生过什么 | ✅ biography 事件流 + digest 注入 |
| 状态（面向未来） | 知道正在做什么、卡在哪、下一步 | 🟡 dev.tasks 的 goal/stated/approaches 是雏形，但依赖会话推进 |
| 循环（自主性） | 有自己的时钟，能评估"现在有没有该做的事" | ❌ 缺失，所有感知与行动都由用户输入触发 |
| 授权（边界） | 知道哪些事可以不问就做 | ❌ 缺显式模型（隐式、二元） |

**两个痛点的解法不同**：
- 冷启动成本（每次重新解释上下文）→ 状态注入可解（dev.tasks 开场简报已有雏形）
- 触发成本（需要用户想起来该做）→ 只能靠循环解：用户忘了，系统得记得

## 2.2 核心架构判断：主键翻转

现在 zion-next 一切资产的 primary key 是 session（会话持有终端、工具授权、任务上下文）。心智化的本质动作是把主键换成 user：

- **会话降级为 IO 通道**——心智与用户交互的方式之一，不是心智本体
- **新增常驻循环（Mind Loop）**，跑在 scheduler 上，以用户为主键：

```
心跳 → 读状态（tasks/projects + biography + profile）
     → 评估（哪些状态卡过期？dormant 方案被环境信号唤醒？用户说过的"周二开跑"有人跟进吗？）
     → 决策（沉默 / 写入收件箱 / 直接行动）
     → 行动 / 汇报
     → 结果回写事件流（反射弧闭合）
```

评估和决策是新的，其余全是现有组件复用：scheduler 是心跳、agents 是行动、projects 是状态、biography 是记忆。**不需要新地基，需要把它们串成以用户为中心的环。**

## 2.3 主动性阶梯（L0-L3）

| 档位 | 行为 | 打扰成本 | 前置条件 |
|---|---|---|---|
| L0 静默观察 | 只更新状态 | 0 | 已具备 |
| L1 带上下文应答 | 会话开场注入状态简报 | 0 | 🟡 已有雏形 |
| L2 主动汇报 | 心跳发现机会/风险 → 收件箱 | 低 | 需要心跳循环 |
| L3 受限自主 | 授权域直接执行、事后汇报 | 高 | 需要授权模型 + L2 验证 |

**关键设计：L2 是 L3 的必经之路，不可跳级。** 用"主动汇报的采纳率"挣自主权——连续采纳 N 次后才谈判升级为直接执行。绿区候选：日报类（高确定性、可回滚、用户已高度放权的重复任务）。

## 2.4 端到端 7 环节与每环卡点

```
① 触发面 → ② 蒸馏 → ③ 投影 → ④ 注入 → ⑤ UI → ⑥ 心跳 → ⑦ 收件箱
```

| 环 | 内容 | 卡点 | 对策 |
|---|---|---|---|
| ① 触发面 | chat/runFinished，排除 comment/scheduled/agent/task | scheduled 会话不蒸馏：定时任务产出从不进记忆，感知带宽砍半 | 放开 scheduled（保留 comment/agent/task 排除）；用更严契约对冲噪音（例行成功不记，只记异常/偏差/里程碑） |
| ② 蒸馏 | 契约 + state 扩展（铁律） | **全链最大卡点：状态语义不可靠**——模型会过度推断 nextAction/blocker | state 只写输入中明确出现的状态（禁止推断）；owner 必填；未确认 state 一律候选态，一票否决下行；架构假设违约必然发生 |
| ③ 投影 | 确定性纯函数 events→状态卡 | project 键不稳定 → 卡片分裂 | alias 归一表 + 心跳"疑似同项目合并"提示 |
| ④ 注入 | buildIdentityContext 加状态块 | 快照冻结 vs 状态鲜活；注意力预算（现有 ~4000 字符） | 状态块不走快照（每次重读，60s 内存缓存）；top5 卡 ×160 字符上限 |
| ⑤ UI | 状态面板 + 确认按钮 | 人时成本最大、可后置 | "确认"按钮是唯一不可替代价值（候选转 confirmed）；其余文件即 UI |
| ⑥ 心跳 | 规则层（零 LLM）+ 条件 LLM 层 | app 在线依赖；错误打扰 | 规则层独立于 app（cron 兜底）；LLM 层缺省降级；条目带来源可溯源；每日 ≤3 条 |
| ⑦ 收件箱 | inbox 文件 + 注入 | 文件状态如何回写 WAL（勾选不被自动感知） | 心跳 diff inbox 与快照，把"已勾/已划"转成事件写回 |

## 2.5 卡点排序（当时的明确判断）

| 排名 | 卡点 | 致命性 | 说明 |
|---|---|---|---|
| 1 | ② 蒸馏状态语义不可靠 | 🔴 源头污染 | 下游全毁；对策=铁律+候选态一票否决 |
| 2 | ⑤ 确认回路缺失 | 🔴 错误累积 | confirmed 只是字段，无纠正机制；信任崩塌后不可逆 |
| 3 | ③ project 键不稳定 | 🟡 卡片分裂 | =状态丢失 |
| 4 | ① scheduled 不蒸馏 | 🟡 感知带宽 | 定时任务是最有价值的节奏信号 |
| 5 | ④ 注入预算/注意力 | 🟡 边际稀释 | top5 卡、1000 字符上限 |
| 6 | ⑥⑦ app 依赖/回写断裂 | 🟢 可工程解决 | cron 兜底 + inbox diff 回写 |
| 7 | ⑤ UI 人时 | 🟢 后置 | 文件即 UI |

**一句话结论**：卡点 1 和 2 是同一个问题——"模型说错了怎么办"。只要"未确认状态永不下行到行动"这条红线焊死，其余都是工程量；这条线焊不牢，后面每个环都在放大一个谎言。

## 2.6 最小闭环（绕过最大卡点的第一版）

```
现有事件回放 → 状态投影 → 卡片（冷启动当天即有）
   ↓
蒸馏契约 + state 铁律（未确认=候选）
   ↓
注入状态块（不走快照）
   ↓
规则层心跳（纯脚本+cron）→ 收件箱（每日 ≤3 条）
   ↓
inbox diff 回写 WAL
```

刻意不做（等数据）：UI 面板、LLM 心跳层、scheduled 放开。

> 注：以上是讨论中段的架构。最终方案（04 文档）有重大简化：状态投影环节被「主模型直接维护项目活文档」取代——理由是有实验证据表明主模型（完整上下文）比独立蒸馏（只看到最后一轮）更可靠，且"像 skills 那样"的文件方案认知负担最低。
