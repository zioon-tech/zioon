更和谐的工作台需要先统一层级

当前的问题不是某一个图标或某一个圆角，而是几个区域的视觉语言不一致：Activity bar 像一级导航，sidebar 像数据列表，editor header 像工具条，bottom status 又像插件入口。原型里先把这些角色分清。

建议原则

普通列表用整行柔和底色表达选中；一级导航可以保留更明确的 indicator；状态栏只承载低干扰信息，不和 bottom panel tabs 抢层级。

方案 A · 安静聚焦

最稳妥的演进路线：沿用现在布局，统一图标、间距、选中态和 panel 层级。改动成本低，适合作为 zion-next 默认视觉。

适合场景 默认 长期编辑、会话管理、轻量调试。
视觉策略 重点 弱化重边框，使用整行柔和底色和语义图标建立秩序。
风险 注意 如果继续叠加插件入口，status bar 仍可能变拥挤。

逐模块优化建议

这里不是最终 CSS 方案，而是把每个区域应该承担的视觉职责先固定下来。后续落地时，每个模块都可以独立推进。

Activity bar

  • 保留一级导航的强识别，但只在这里允许 indicator。
  • 图标必须语义明确：会话 history、插件 extensions、智能体 agent、LLM bug。
  • 避免把所有入口都做成同等重量，设置和命令应沉到底部。

Sidebar / Session manager

  • 会话列表更像 inbox，不像文件树；优先突出会话标题、时间、tokens、关联文件。
  • 当前会话用整行底色，不加左侧高亮条。
  • 文件夹和标签可以作为轻量分组，不要抢会话标题层级。

Editor workbench

  • Header 只放当前文档、TOC、分屏、运行等高频操作。
  • 正文区域保持安静，工具调用卡片用低饱和边框承载状态。
  • 右侧 auxiliary bar 适合上下文、评论、记忆等辅助信息。

Bottom status bar

  • 只放低干扰、短文本、可点击状态；不要承载复杂列表。
  • Terminal 状态应该是小 chip，不应该像 panel tab。
  • 模型、工具、上下文指标可以分组显示，减少“满地按钮”的感觉。

Bottom panel

  • Output、Terminal、LLM 请求是同一层级，tab 样式要统一。
  • 日志内容使用 mono 字体和低对比背景，减少抢 editor 注意力。
  • 打开时高度稳定，避免每个插件自己定义一套 panel 语言。

Memory / Context

  • Memory 文件夹/文件必须和 Files panel 同一套图标语言。
  • Context 更适合 layers，而不是 @ 这种输入符号。
  • Comments、Agents、Memory 的入口都应有图标，避免空白破坏节奏。

Session-manager 的三种具体做法

会话管理是最容易显得乱的地方。下面三种方案可以单独挑，也可以混合：比如默认用 A，重度模式提供 C。

1. Inbox 列表

最推荐。会话像邮件列表一样扫描，适合日常默认模式。
